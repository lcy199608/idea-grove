# 聊天参考图随文档沉淀

## 选择与呈现

用户上传的图也属于讨论资料。整理时主动回看本次相关附件：对美术风格、配色、界面布局、玩法关系、关卡结构或技术问题有明确参考价值的图，加入待保存文档；用户明确要求保留的图应保留。无关截图、废案、重复图不自动收集。图片只含糊“好看”而无法确定用途时，先说明判断或提出一个必要问题。

在整理预览中，连同文字列出图片名称/序号、参考用途和拟插入模块的位置。AI 判断为有用但用户尚未采用的内容仍是 exploring，不能擅自标为 confirmed。每张图紧邻它说明的段落，并附一句用途/适用边界，例如“参考冷暖配色，不沿用角色造型”。正文插图不应统一丢到附件末尾。

“整理”只做预览；用户要求保存本次讨论或指定模块时，相关有意义的参考图默认包含在保存范围，不再让用户逐张执行上传或重复确认。用户说“只保存文字”“不要存图”则优先执行。纯上传图片或普通聊天不触发远端写入。

## 原文件能力门槛

实际看见图像可以做语义分析，但**不等于拿到了可保存的原始字节**。必须先找到当前环境明确提供的附件文件路径、授权文件读取工具，或平台给出的可用下载引用。不能从缩略图、文件名或视觉 token 编造二进制，不能把占位图/重绘图冒充用户参考图。

- Codex：读取本条消息明确附带的本地图片路径；必要时用 view_image 看图。
- ChatGPT 有附件可读的文件处理/代码运行环境：在该环境读取上传文件，使用随插件提供的 `scripts/prepare_reference.py`，或根据本节协议进行等价处理。脚本属于插件资源，不要求连接用户电脑；若宿主未挂载脚本，可把脚本放进当前文件处理环境再调用。不假设普通聊天总有此能力。
- 只有 file_id 而没有可读文件工具，或只有模型可见图片而无原文件时：明确指出缺少原文件通道，不虚构 URL、不访问私有内部端点。优先提示在支持附件文件处理的 ChatGPT Work 中继续；可提供用户重新附上原文件或 Web 插入的恢复方式。普通 GitHub create_blob 只收 Base64 字符串，不能把 file_id/path 直接当作 content。
- 已提供的临时下载引用只能由授权文件工具在来源允许的范围内读取；不要把临时链接、file_id、凭据或本机路径写进文档作为永久图片地址。

## 准备图片

先确定真实的主题与模块 ID；一个模块最多 10 图，整个资料库二进制图片不超过 40 MiB。读取最新模块附件及 tree 中图片 size，预检本次新增后的总量。重复上传的同一张图优先复用同模块已有附件与引用；同一附件不能跨模块直接引用，需要跨模块展示时遵循 schema 的独立附件路径规则。

有 Python/Pillow 时调用资源脚本：

```sh
python3 /技能目录/scripts/prepare_reference.py --source /真实附件路径 --output-dir /全新的临时输出目录 --topic TOPIC_ID --module MODULE_ID --caption '参考用途'
```

输出目录必须新建以避免覆盖；不要批量扫描用户的其他图片目录。stdout 只含元数据和文件路径；`blob.json` 包含精确 Base64，`reference.json` 包含附件、相对 Markdown 引用、预期 Git blob SHA 和临时文件位置。它们是上传准备材料，不能作为仓库正文/附件文件直接写入。

输入最多 20 MiB/5000 万像素，输出静态 WebP、最长边 2560、单图 1.5 MiB。按 EXIF 调整方向、保留透明度、去掉 EXIF；不重新绘图、不加水印或改变内容。动画只取首帧，必须明确告知。将脚本返回的 notes 纳入回复。若缺少 Pillow，可用当前已具备的等价图像工具；不要静默安装依赖或声称已压缩。转换不是功能测试，只有真实保存请求才实际处理图片。

## 上传与正文同次提交

1. 用户要求保存后，先准备本次所有选中图片。任何必需图片不可读/处理失败时默认停止整次图文保存，保留草稿并明确未保存；不能静默只保存文字或插入坏链接。用户明确选择先存文字时，报告哪些图待补。
2. 通过代码把 blob.json 中的精确字符串送进 GitHub `create_blob(repository_full_name, encoding="base64", content=...)`；不要让语言模型转录、猜测或截断 Base64。使用宿主提供的工具编排/文件传输能力，避免把大段 Base64 回显到聊天。工具无法接收完整数据时停止该次保存，不能编造上传结果。
3. 在支持 functions.exec 与 exec_command 的环境，在编排代码中循环调用 `python3 /技能目录/scripts/read_blob_chunk.py --blob /准备目录/blob.json --offset OFFSET --limit 8192`，每次设 max_output_tokens 至少 10000；用 `JSON.parse(result.output)` 捕获数据，只保存在编排变量中。检查每次 exit_code 为 0、offset 连续、next = offset + content.length、total 一致且 next 前进，直到 next = total，拼接长度须等于 total。程序化将完整字符串传入 create_blob，仅输出返回的 SHA，不把分块回显给模型再手动拼接。长操作可分批调用，用编排环境 store/load 保存进度。路径采用严格 shell 引号处理。任何截断、解析错误或宿主请求体上限都会停止上传，不降级为残缺图片。其他环境用等价的受支持工具桥接，不能假设它具备这些具体工具。
4. 返回 blob SHA 应与计算所得 gitBlobSha 一致；不一致或上传失败不创建引用该图的提交。图片 blob 上传不改变分支，不代表保存成功。
5. 在最新 base_tree 上加入 `{path: attachment.path, mode:"100644", type:"blob", sha:<真实返回 SHA>}`；同次更新模块 attachments（inline:true）、正文相对引用和邻近用途说明、topic.updatedAt，并把 idea-vault.json 升到 schemaVersion:2，保留其他字段。
6. 图片、元数据、模块与标记进入**同一提交**，按 github.md 非强制更新分支。并发时重读，保留不相关改动；同模块冲突停止。失败时不能只补做一个含坏图片引用的文字提交。
7. 本地 Git 通道可把准备好的真实图片复制到已确认资料仓库相应路径，写元数据与正文后同次提交。仍不得把创意写进应用源码仓库。
8. 成功回复包含保存的图片数量、用途、所属模块和真实提交链接；说明 Web 拉取即可在文中看到图片。最终只按分支更新成功报告已沉淀，不将准备文件、blob 或临时下载链接当作完成。
